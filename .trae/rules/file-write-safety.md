# 文件写入与编码安全

## 适用范围

本规则用于约束 AI 在项目中创建、修改、覆盖、批量编辑文件时的行为，目标是保证变更可审查、编码不损坏、范围不扩大、风险可回滚。

## 核心原则

- 写文件前必须确认目标文件、修改范围和预期变更，不得基于模糊记忆猜路径、变量名或文件内容。
- 修改既有文件前，必须先读取最新内容。
- 涉及多个文件时，必须检查相关文件之间的联动关系。
- 优先使用带 diff 预览、可审查、可回滚的编辑方式。
- 避免使用不可审查、不可回滚或容易隐式转码的 shell 写入方式。
- 含中文或非 ASCII 内容的文件必须特别注意编码安全。
- 只修改用户请求范围内的内容，不借写文件之机顺手重构、格式化、重排或改动无关代码。

## 禁止行为

未经用户明确授权，禁止使用以下方式修改文件：

- 使用 `Set-Content`、`Out-File`、`>`、`>>`、`tee` 等方式直接覆盖或追加文件。
- 使用 `sed -i`、内联脚本、一次性 shell 命令批量改写文件。
- 在终端命令中通过 `python -c`、`node -e`、`echo >` 等方式生成或覆盖项目文件。
- 整文件重写含中文、非 ASCII、配置项、复杂业务逻辑或用户未要求修改的大文件。
- 在未查看 diff 的情况下声称修改完成、验证通过或问题已修复。

例外：如果用户在当前对话中明确授权了具体命令和具体目标文件，执行后必须立即复核 diff，并报告实际变更。

## 操作分级

### L1：只读操作

读取文件、搜索文本、查看目录、查看 Git 状态属于只读操作，可以直接执行。

### L2：局部修改

单文件、单点、可精确定位的局部修改，可以直接使用可审查的编辑方式执行，但必须保证 diff 清晰、范围最小。

### L3：大范围修改

以下情况属于大范围修改，执行前必须先列出影响范围并等待用户确认：

- 整文件重写。
- 跨 3 个以上文件的修改。
- 超过 100 行的批量变更。
- 批量替换、批量重命名、批量移动文件。
- 修改公共类型、公共接口、核心配置或项目结构。

### L4：不可逆或高风险操作

以下操作必须先查看 `git status`，并等待用户明确确认：

- 删除文件或目录。
- 覆盖未提交修改。
- 修改生成物、迁移文件、锁文件、密钥文件、环境配置。
- 执行可能导致无法恢复的批量写入。
- 对未提交工作区进行大范围重写。

如果工作区不干净，必须提醒用户先 commit、stash 或明确授权继续，不得静默覆盖。

## 编码安全要求

- 写入前应识别文件是否包含中文、非 ASCII 字符或特殊换行格式。
- 对含中文或非 ASCII 的文件，优先使用局部精确修改，避免整文件重写。
- 必须整文件重写时，写后应立即回读关键片段，确认没有出现 `?`、`�`、乱码、异常换行或内容丢失。
- 不得使用会隐式改变编码、换行符或 BOM 的方式写入文件。
- 发现编码不明、内容异常或 diff 无法可靠展示时，必须停止并询问用户。

## 写入前自检

执行任何文件修改前，必须确认：

- 已读取目标文件的最新内容。
- 修改方式支持 diff 审查。
- 修改范围符合用户请求，没有扩大任务边界。
- 不会隐式改变编码、换行符或文件结构。
- 如涉及大范围修改，已确认 Git 工作区状态并获得用户许可。
- 如 `old_str`、匹配文本或目标位置存在多处匹配，已停止并请求用户确认。

## 写入后复核

文件修改后必须复核：

- diff 是否只包含预期变更。
- 是否误改无关文件、格式、换行、缩进或排序。
- 含中文或非 ASCII 文件是否无乱码、无替换字符、无内容截断。
- 多文件变更是否保持引用、类型、导入、路径和配置一致。
- 如未实际运行测试，不得声称“已验证通过”。

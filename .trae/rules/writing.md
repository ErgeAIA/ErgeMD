# 内容输出风格

## 触发场景

本规则按上下文激活：

- 写代码注释时，应用「代码注释」规则。
- 写 README、技术文档、项目说明时，应用「技术文档」规则。
- 写教程、课程稿、视频脚本、B 站文案时，应用「教程与视频脚本」规则。

不要混用风格。不同内容类型应使用不同表达方式。

## 通用原则

- 先给结论或最小可用结果，再解释原因。
- 避免空泛铺垫、重复总结和无效客套。
- 内容应服务于读者完成任务，而不是展示作者知道很多。
- 复杂内容应拆成清晰小节，但不要过度列表化。
- 不确定内容必须标注「待验证」或「需人工审查」。
- 不得把猜测、经验判断或未验证信息写成事实。

## 代码注释

- 注释解释“为什么”，不重复描述“做了什么”。
- 不写翻译式注释，例如 `// increment i`。
- 对复杂业务规则、边界条件、兼容逻辑和风险点必须补充注释。
- 复杂算法可以补充时间复杂度、空间复杂度或关键取舍。
- TODO 必须写清楚责任和具体事项，例如 `// TODO(@me): 补充取消任务的边界测试`。
- 不保留过期注释；修改逻辑时必须同步检查相关注释是否仍准确。

## 技术文档 / README

- 每个核心概念优先给最小可运行例子，再讲原理。
- 用例子和反例对比，比纯描述更有效。
- 安装、配置、运行、验证步骤必须可执行、可检查。
- 命令块必须标注语言，例如 `powershell`、`bash`、`ts`。
- 截图、图片和附件路径应遵循项目已有目录约定。
- 避免使用“显而易见”“众所周知”“相信大家都知道”等表达。
- 文档中的路径、命令、配置项必须与项目实际内容一致。
- 无法确认的命令或路径必须标注「待验证」。

## 教程与视频脚本

- 开头应直接抛出问题、痛点或收益，不寒暄。
- 每个步骤都应说明“为什么这么做”。
- 关键操作应明确、可复现、可暂停。
- 不隐藏关键步骤，不留暗坑，不用模糊说法替代操作细节。
- 结尾应给出可直接复用的完整代码、配置或检查清单。
- 面向视频平台时，关键命令、路径、按钮和结果应适合字幕化展示。
- 避免外链导流式表达，核心信息应在正文内讲清楚。

## 交付前检查

- 是否满足用户指定的文体、语气和用途。
- 是否存在未验证事实。
- 是否有过时路径、命令、截图或配置。
- 是否有与项目实际情况冲突的说明。
- 是否把复杂内容讲成了不可执行的概念堆砌。
- 是否有不必要的客套、空话或重复内容。

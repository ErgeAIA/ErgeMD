## 3. 问题清单

### 高（正确性，建议优先）

**H1 · chunk 解析缓存键可跨文档碰撞，且无淘汰上限**
- 维度：质量（正确性）
- 结论：`CHUNK_PARSE_CACHE` 的 key 仅由 `startLine-endLine` 与首末行**长度**组成，不含文档标识或内容哈希；两个不同文档在相同行范围且首末行长度相同时返回对方的 blocks。缓存为模块级 `Map`，无容量上限，随打开文档数单调增长。
- 证据：`src/utils/markdownBlocks.ts:511-521`（key 构造）、`src/utils/markdownBlocks.ts:536`（读取）、`src/utils/markdownBlocks.ts:923`（写入，无淘汰）
- 方向：key 加入内容哈希或文档实例 id；加 LRU 容量上限。

**H2 · BUG-030 的修复不在当前代码中（宽松 isTableLine 回归）**
- 维度：质量（正确性 + 回归）
- 结论：`isTableLine` 回到「任何含 `|` 的行即判表格」的宽松版，普通文本中的管道符会把段落误并入表格块；BUG-030 记录的「收紧判断 + isTableSeparator」修复丢失。根因是解析逻辑有两份重复实现，修复需同步两处，历史上已因此丢失。
- 证据：`src/utils/markdownBlocks.ts:72-75`（宽松判断，且 `/^\|/` 被第二个条件包含，`stripInlineCode` 定义了却未用）；对照 `docs/agents/debug-log.md` BUG-030；重复实现见 `src/utils/markdownBlocks.ts:123-509`（parseMarkdownBlocks）与 `src/utils/markdownBlocks.ts:523-926`（parseChunk），约 380 行/份
- 方向：按 BUG-030 收紧判断并同步两处；长期将两份实现合并为单一参数化解析器。

**H3 · 多 Tab 下 `querySelector(".markdown-body")` 命中错误文档**
- 维度：架构（正确性）
- 结论：所有 Tab 的 ReadingArea 常驻 DOM（display:none 切换），`document.querySelector(".markdown-body")` 按文档序取第一个，可能是非活动 Tab；搜索高亮 / 清除 / 全选会作用于错误文档。虚拟滚动模式下另有一个叠加限制：搜索基于 DOM TreeWalker，只覆盖已渲染块，视口外匹配不可见。
- 证据：`src/components/reader/SearchBar.tsx:41,62,120`、`src/App.tsx:366`；Tab 常驻机制见 `src/App.tsx:728-741` 与 `src/components/reader/ReadingArea.tsx:365`；搜索遍历见 `src/components/reader/SearchBar.tsx:127-130`；虚拟渲染范围见 `src/components/reader/VirtualMarkdownView.tsx:219-241`
- 方向：按 activeTabId 经 ref 定位容器，禁用全局 querySelector；搜索改走 content 字符串扫描并维护匹配索引，不依赖渲染结果。

### 中（性能，静态推断，需实测复核）

**M1 · 大文档打开的全量解析抵消了 chunked 设计**
- 维度：性能 / 架构
- 结论：虚拟模式本为避免全量解析，但 `ReadingArea` 为取 TOC 对**全文**调用 `parseMarkdownBlocks`；叠加 `App.tsx` 的 `extractTOC` 全文扫描，大文档打开至少发生 2 次全文遍历 + 1 次 chunked 初始块解析，且都在主线程同步执行。
- 证据：`src/components/reader/ReadingArea.tsx:59-63`（useMemo 内全文 parseMarkdownBlocks）、`src/App.tsx:197-207`（extractTOC）、`src/utils/toc.ts:123,140`（全文 split + 逐行扫描）、`src/components/reader/VirtualMarkdownView.tsx:51-70`（chunked 仅初始块）
- 方向：`virtualTocItems` 改消费 VirtualMarkdownView 已算出的 `initialTocItems`（回调上行或提升状态）；中长期收敛为「一次解析、多处消费」。

**M2 · 标题检测三套实现分叉**
- 维度：架构（一致性）
- 结论：toc.ts、parseMarkdownBlocks、parseChunk 各有一份标题检测，正则存在差异（如 ATX 是否要求 `#` 后有空格：`toc.ts:168` 允许 `\s*`，`markdownBlocks.ts:247` 要求 `\s+`；setext 条件也不同），小文档 TOC（toc.ts）与大文档 TOC（parseMarkdownBlocks）可能给出不同结果；TOC 坐标体系也不同（logicalOffset vs blockIndex）。
- 证据：`src/utils/toc.ts:164-210`、`src/utils/markdownBlocks.ts:246-278`、`src/utils/markdownBlocks.ts:667-699`
- 方向：抽出单一 heading 检测模块统一消费；统一 TOC 坐标或保留显式映射层。

**M3 · 所有 Tab 全量常驻（内存 + 解析结果 + DOM）**
- 维度：性能 / 架构
- 结论：`tabs.map` 为每个 Tab 渲染 ReadingArea 并保持挂载，各自持有解析结果与完整 DOM 树；fileStore 中全部 Tab 的 `content` 常驻内存。多开大文档时内存与首屏外的维持成本随 Tab 数线性增长。
- 证据：`src/App.tsx:728-741`、`src/components/reader/ReadingArea.tsx:363-399`（display 切换）、`src/stores/fileStore.ts:86`（content 入 TabInfo）
- 方向：非活动 Tab 懒挂载（滚动位置已有 percentageCache 可恢复）；或对常驻 Tab 数设上限，超出者卸载 content。

**M4 · 导出在主线程生成全量 HTML 并整串过 IPC**
- 维度：性能
- 结论：PDF 导出在主线程同步生成完整 HTML（含主题 CSS 与图表渲染结果），再以单次 IPC 把整串传给 Rust；大文档会明显卡 UI，且无进度反馈。
- 证据：`src/utils/exportPdf.ts:41,48,52-55`
- 方向：HTML 生成移入 Web Worker 或分批；至少补进度提示。注：导出独立管线本身是 DEC-023 的裁决，不动该架构。

### 低（质量 / 技术栈 / 卫生）

**L1 · assetProtocol 全开但零使用**
- 维度：技术栈（攻击面）
- 结论：代码中 `convertFileSrc` / `asset://` 零引用（图片已按 DEC-028 改 base64），`assetProtocol.enable: true` + scope `["**"]` 是无用途的攻击面。
- 证据：`src-tauri/tauri.conf.json:36-41`；全仓 `*.ts/tsx/rs` 搜索 `convertFileSrc|asset://` 0 命中；背景见 DEC-028
- 方向：关闭 assetProtocol，或至少把 scope 收紧到具体目录模式。

**L2 · 死表与缺失的版本化迁移**
- 维度：架构（数据层）
- 结论：`workspaces` 表建而不用（命令清单中无任何 workspace 读写）；`schema_version` 表存在但迁移仅为 `CREATE TABLE IF NOT EXISTS`，无版本化迁移路径，后续 schema 变更无机制可依。
- 证据：`src-tauri/src/db/mod.rs:51-59,61-74`；`src-tauri/src/lib.rs:208-229`（invoke_handler 清单无 workspace 命令）
- 方向：删除死表或补工作区持久化；以 schema_version 为基础建立版本化迁移。

**L3 · db_pool 全局 Mutex 样板重复 8 处**
- 维度：质量
- 结论：池经 `Arc<Mutex<Option<SqlitePool>>>` 存取，8 个命令重复同一取锁样板，构成不必要的串行点与重复代码。
- 证据：`src-tauri/src/lib.rs:10-13` 及 `:28-31`、`:51-54`、`:79-82`、`:102-105`、`:126-130`、`:143-146`、`:158-161`
- 方向：init 完成后 `manage(SqlitePool)`，命令直接 `State<SqlitePool>`。

**L4 · 进度保存静默吞错 + wordCount 恒 0**
- 维度：质量
- 结论：`flushReadingProgress` / `flushAllReadingProgress` 两处 `.catch(() => {})` 静默失败（与 BUG-018 教训相悖）；`wordCount` 硬编码 0 传入，DB 列永不更新，而 StatusBar 已算出真实 wordCount 却未传入。
- 证据：`src/utils/readingProgress.ts:33,35-37,51-54`；wordCount 计算见 `src/App.tsx:216-219`
- 方向：失败至少 `console.error`；保存时传真实字数。

**L5 · App.tsx 单组件 819 行**
- 维度：质量（可维护性）
- 结论：启动恢复、文件关联双路径、拖拽、导出菜单、TOC、进度等约 15 个 effect/state 与全部业务回调集中在同一组件；任一 state 变化的重渲染波及全树（子组件有 memo 缓解）。
- 证据：`src/App.tsx:39-637`
- 方向：按域拆分 hooks/子组件（启动恢复 / 文件关联 / 拖拽 / 导出动作）。

**L6 · pinTab 两分支完全相同**
- 维度：质量（死代码）
- 结论：if/else 两个分支执行同一逻辑。
- 证据：`src/stores/fileStore.ts:201-219`
- 方向：合并为单分支。

**L7 · 文件树无虚拟化且默认全展开**
- 维度：性能（大工作区）
- 结论：`FileTreeNode` 默认 `isExpanded = true`，无虚拟化；数千文件的工作区会一次性渲染全部节点。
- 证据：`src/components/panels/FileList.tsx:32`
- 方向：默认仅展开根层；大树虚拟化或分批渲染。

**L8 · BUG-028 记录的修复与代码漂移**
- 维度：质量（记录与实现不一致）
- 结论：BUG-028 记录「改用 visibleRange 中部 block 索引」，当前代码仍取 `visibleRange[0].index`；点击跳转场景有 isScrollingRef 保护，但非交互滚动的章节尾部露出场景仍可能高亮偏移。
- 证据：`src/components/reader/VirtualMarkdownView.tsx:152-154`；对照 `docs/agents/debug-log.md` BUG-028
- 方向：确认是有意回退还是回归；若需修按 BUG-028 记录恢复中部索引。

## 5. 方向摘要（按优先级，不动栈）

1. **先修正确性**：H1（缓存键加文档标识 + 容量上限）、H2（isTableLine 收紧并同步两处）、H3（容器定位改 ref/activeTab，搜索走数据层）。
2. **单一解析源**：M1 + M2 合并解决——一次解析产出 blocks + TOC，chunked 初始结果直接上行为 virtualTocItems，toc.ts 的全文扫描退位；这是投入产出比最高的一项。
3. **按需挂载**：M3——非活动 Tab 卸载渲染树（进度有缓存可恢复），把「常驻」换成「可恢复」。
4. **攻击面与数据层卫生**：L1（关 assetProtocol）、L2（死表清理 + 版本化迁移）、L3（池直接注入）。
5. **工程卫生**：L4~L8（吞错、wordCount、App 拆分、死代码、文件树虚拟化、BUG-028 漂移确认）。

**基线优势（改动时勿破坏）**：Mermaid 的串行队列 + 容量/时效缓存 + 懒加载（`MermaidDiagram.tsx:10-56`）；scroll 处理的 rAF + 100ms 节流 + ref 模式（`useReadingProgress.ts:51-88`）；settingsStore 的 persist merge（BUG-019 修复到位）；rehype-sanitize 自定义白名单与 data:image 放行的取舍（`MarkdownBlockView.tsx:45-82`）；导出独立管线（DEC-023）；文件关联冷热双路径（DEC/BUG-049 修复到位）。

# frontend/theme-tokens — 主题令牌与配色工程经验

## F8: token 消费完整性门禁 🔴

- **主张**：设计令牌（CSS 变量）体系必须配「消费完整性门禁」——任何无兜底（即 `var(--x, fallback)` 之外的裸 `var(--x)`）的消费方，其变量必须 ⊆（主题文件定义 ∪ 非主题 CSS 定义）；不满足即门禁拦截，不能靠运行时静默失效。
- **适用**：任何用 CSS 变量 / 设计令牌做主题切换的项目。
- **Why**：CSS 自定义属性无兜底时，若从未被定义，属性直接失效且不报错——「消费了但没人定义」是静默缺陷，没有门禁的体系里长期潜伏。本次 7 处 `LinkEditModal`/`ImageEditModal`/`ReadingOptions` 消费 `--bg-primary`，而它从未被任何主题或 base 层定义，弹层背景长期透明/继承却无人察觉。
- **How**：`src/styles/__tests__/theme-generate.test.ts` 收集所有主题文件 + base 层声明的变量集合，解析组件中裸 `var(--x)` 消费方，断言每个 `--x` 都在定义集合内；引入新 token 时要么在源色表定义，要么显式别名（如 `bg-primary → canvas.secondary`）。
- **反例**：历史消费方用 `--bg-primary`，而 ErgeMD 画布族命名是 `bg-page/reader/sidebar/code/secondary/tertiary`，无 `bg-primary`——命名漂移致 7 处背景静默失效（BUG-067）。
- **事实源**：BUG-067；`src/styles/__tests__/theme-generate.test.ts`；DEC-035

## F9: 派生色按对比度调校到阈值边界 🟡

- **主张**：品牌色 / 强调色 / 标题色等「功能位色」若原始值过不了对比度护栏（≥4.5:1），不要将就使用裸品牌色，也不要随意改色相，而是用 `tuneForContrast` 只推明度（色相 H、彩度 C 尽量不动）把对比度调到刚过门槛的边界值。
- **适用**：主题色板派生、强调色 / 链接色 / 标题色选型。
- **Why**：裸品牌色往往为满足视觉冲击牺牲可读性（solarized-light 列表序号色 3.59:1 低于门槛）；但品牌色相/彩度是身份资产，全改会丢失主题辨识度。只调明度能在「可读」与「保身份」间取平衡。
- **How**：`scripts/theme/color-science.js` 的 `tuneForContrast(base, target, minRatio)` 在 OKLCH/Lab 空间沿明度轴二分搜索最小变动解；门禁（`theme-contrast.test.ts`）守护结果 ≥4.5。
- **反例**：直接把功能位色设成原始品牌色 → 浅底上文字对比度不足、长期不可读（solarized-light 序号色被门禁抓出 3.59:1）；或为避免冲突把色相也改掉 → 主题辨识度丢失。
- **事实源**：DEC-035/036；`scripts/theme/color-science.js`；BUG-068

## F10: 主题存在理由优先于机制统一 🟡

- **主张**：当「统一机制」与「某主题的存在理由（身份）」冲突时，优先保主题身份；统一是为体验服务，不是反过来。
- **适用**：多主题色板设计，尤其含「纯灰度 / 高对比 / 暗夜」等特型主题。
- **Why**：机制统一（如所有主题 fill 都按同一 `fillBand` 派生）会让 monochrome 主题被迫带彩度，失去其「纯灰度」的存在价值；特型主题之所以存在，正是因为它偏离了默认机制。
- **How**：monochrome 主题的 `fillBand` 显式设 `C: 0`（彩度为 0），让派生公式在该主题下输出纯灰阶，而非强行套用彩色 fillBand；其它主题照常彩色派生。
- **反例**：为统一把 monochrome 也纳入彩色 fillBand → 纯灰度主题被染上彩度，身份丧失（DEC-036 阶段定的「monochrome 的 C=0 是牺牲机制统一性换来的主题身份」，R13/R14 收口确认）。
- **事实源**：DEC-036；R13/R14 收口记录

## F11: CSS 派生层导入顺序陷阱 🟡

- **主张**：CSS 派生层（如从主题契约变量再派生的 `divider` / `table-border` 层）若导入顺序晚于主题文件，且选择器特异性相同（0-1-0），会覆盖主题契约值；派生层应只声明自身新增变量，不重复声明契约已定义的变量，或导入顺序早于契约消费方。
- **适用**：多层 CSS 变量体系、生成式样式层。
- **Why**：CSS 同特异性下后声明者胜；派生层晚导入即「后声明」，会把契约里精心校准的值覆盖成派生层的默认值，且静默发生。
- **How**：R14 收口——把 `divider` / `table-border` 的派生逻辑从派生层移除，改由主题契约统一提供，消除「晚导入覆盖」；派生层只保留无法从契约派生的极少数字段。
- **反例**：派生层晚导入且重复声明 `--divider` / `--table-border` → 主题契约校准的边框色被覆盖，R13/R14 收口时发现并移除（DEC-036 阶段）。
- **事实源**：DEC-036；R13/R14 收口记录

## F13: 默认映射层用 `:where()` 把特异性降为 0 🟡

- **主张**：当「默认映射层」与「可覆盖层」特异性相同（如 `[data-theme]` vs `[data-theme="x"]`）且默认层后导入时，把默认层选择器包进 `:where()`——特异性降为 0，覆盖层稳定生效。这是 F11（消除重复声明）之外的第二种解法，两者适用条件不同、并存不冲突。
- **适用**：多层 CSS 变量体系中「框架提供默认值、使用方可覆盖」的映射层（设计系统的 core 默认层 vs 主题层）。F11 适用「派生层本不该重复声明契约变量」，本条适用「默认值理应存在、但要允许被覆盖」。
- **Why**：`[data-theme="x"]` 与 `[data-theme]` 特异性**完全相同**（都是单个属性选择器，(0,1,0)），并非「带属性值的更高」；同特异性下后导入者胜。若 core 在主题之后导入，core 的默认映射会静默压过主题定义——主题定制全部失效，而源码里主题明明写了正确值，极难从代码看出问题。
- **How**：core 默认层写 `:where([data-theme]) { --token: <default>; }`（只降特异性、不改变匹配，无 `data-theme` 时行为不变）；覆盖层保持 `[data-theme="x"] { --token: <value>; }`。验证用真浏览器 `getComputedStyle(el).getPropertyValue('--token')`，应读到覆盖值而非默认值。
- **反例**：以为「`[attr="value"]` 比 `[attr]` 特异性高」而不做处理 → 默认层后导入即覆盖失效，且因双方都写了同名 token，grep 源码完全看不出谁赢（晨光/夜灯 mindmap 色板「重启后无变化」的直接原因）。
- **事实源**：BUG-077 第三重坑；CSS 层叠最小复现（两种导入顺序对照实测）

## F14: CSS 注释内的 `*/` 会提前闭合并吞掉后续声明 🟡

- **主张**：CSS 注释里禁止出现 `*/` 序列（中英混排、缩写粘连是高发区）；排查「某条声明静默不生效」时，先看它前面那条注释。
- **适用**：所有手写 CSS，尤其注释里写代码标识符、路径、中文与英文缩写混排的场景。
- **Why**：`/*` 注释在第一个 `*/` 处即闭合，其余内容落入规则体；解析器把随后紧贴的声明连同垃圾文本一起吞掉（错误恢复直到下一个 `;`），该声明静默失效、无任何报错。core 的注释「与上方 l*/center 同索引」吞掉了紧随的 `--mermaid-mindmap-branch-0: var(--chart-fill-0);`，造成「同块内唯独一条默认映射失效、其余正常」的诡异现象。
- **How**：写注释避免 `*/` 序列（改写为「l 槽 / center」或加空格）；验证声明是否真生效用真浏览器 `document.styleSheets` 遍历规则或 `getComputedStyle` 读自定义属性计算值，不要只 grep 源文件——源码里有 ≠ CSSOM 里有。
- **反例**：grep 源文件看到声明存在就认为生效 → 实际被注释吞掉，表现为「源码有、运行无」，且同块内仅这一条异常（其余正常），极易误判为别处覆盖而查错方向。
- **事实源**：BUG-077 第三重坑；真浏览器 CSSOM 实测（branch-0 为主题值、branch-1..4 为 core 值）

## F15: 颜色决策必须留在 token 层，渲染层不得反算 🔴

- **主张**：图表/组件的颜色一律由「源色表 + 生成器 + 门禁」决定；渲染层（图表引擎后处理、内联样式）只做布局与结构，**不得按 computed 值反算颜色**。一旦出现「渲染后读实际填充再算文字色」，说明 token 契约已破，应回头补 token 而不是在渲染层打补丁。
- **适用**：任何有主题令牌体系的前端项目，尤其「生成器派生色板 + 图表引擎适配」架构。
- **Why**：内联/后处理取墨会架空令牌体系（用户原话：「那还设计 tokens 干鸡毛」）——同一份色板在不同渲染路径（阅读/导出/预览）各算一遍，口径必然漂移；且内联 `!important` 会压过后续所有样式表规则，主题切换与用户定制全部失效；排查时还会把「契约没覆盖到」误判成「取墨算法不够优」。本轮曾以内联 text-on-fill「修好」文字对比度，多轮反复后仍被整体否决、回归 token。
- **How**：文字色与底色作为**成对 token** 由生成器一次产出（如 `chart-fill-N` × `chart-text-on-fill-N`，用 `pickTextColor` 绑定并保 ≥4.5:1；个别槽位不足时用 `tuneForContrast` 推底色明度，色相不变）；渲染层只注入「哪个槽位给哪个元素」的映射，不计算颜色；对比度由门禁守护。色板还要按画布明暗分化——亮画布取亮档配黑字、暗画布取深档配白字，不能两套主题「除 root 外背景全同、只换文字色」。
- **反例**：在 SVG 后处理里 `getComputedStyle(shape).fill` → 算 ink → 写内联 `color:...!important` → 短期见效，但令牌体系被绕开、导出与阅读口径分裂、主题后续迭代全部失效，最终整体回滚（BUG-077 终局）。
- **事实源**：BUG-077 定稿（用户拍板走 token 路线）；`scripts/theme/generate-themes.js` 的 text-on-fill 与 mindmapHues 生成段
